# ドキュメントと工程記録

## 1. 書き込みの可否

| 対象 | 可否 |
|---|---|
| `docs/spec/CodingSpec.md` | 素案の提示のみ。直接編集を禁止 |
| `docs/spec/BuildSpec.md` | 同上 |
| `Game/AGENTS.md` | 同上 |
| `.agents/rules/` 配下 | 同上 |
| `docs/log.md` | 素案を提示し、人間の承認後に書き込む |
| `docs/STATUS.md` | 素案を提示し、人間の承認後に書き込む |
| `docs/instructions/` 配下 | 同上 |
| `.cs` | 全面禁止 |

規約4種の直接編集を禁じる理由は、規約の改訂履歴そのものが工程記録だからである。
改訂には ADR の発行を伴う場合があり、判断は人間が行う。

## 2. 素案の提示形式

ドキュメントへの追記を提案する場合、以下を必ず併記する。

- 対象ファイルの完全パス
- 挿入位置（何節の後、どの見出しの直前か）
- 見出しレベル

「末尾に追記」のような曖昧な指定をしない。

## 3. 工程記録と現在地の更新

作業を1件終えるごとに、以下の2つを生成する。人間が指示しなくても生成する。

| 対象 | 内容 |
|---|---|
| `docs/log.md` | 経緯・判定・責任の所在を含む追記断片 |
| `docs/STATUS.md` | 進行中の作業、次にやること、ブロッカー、未確認事項の更新差分 |

`docs/log.md` は履歴であり、追記のみを行う。過去の記述を書き換えない。
`docs/STATUS.md` は現在地であり、古い記述を置き換える。
最終更新日を必ず更新する。

作業の途中で新たな未確認事項が判明した場合、その時点で
`docs/STATUS.md` の未確認事項の表に追加する素案を出す。
解消した場合は表から削除し、`docs/log.md` に解消した旨を記録する。

理由: エージェントとのやり取りはリポジトリに残らない。
断片を生成しなければ、判断の経緯が記録から欠落する。
記録自体が本プロジェクトの最優先の成果物である。

## 4. `docs/log.md` の文体

| 項目 | 規則 |
|---|---|
| 文体 | 常体（である調） |
| 見出し | 日付は `## YYYY-MM-DD`、その日の項目は `### 見出し` |
| 箇条書き | `- 項目名: 内容` の形。項目名は名詞句 |
| 折り返し | 1行あたり全角40字前後で改行。継続行は半角2字下げ |
| 表 | 事実の対応関係を示す場合のみ。経緯の記述は箇条書き |
| 判定語 | 「適合」「差し戻し」「未確認」を固定語として使う |
| 主語 | 省略する。行為主体の区別が必要な箇所のみ明示 |

`## 評価指標の定義` は日付に紐づかない恒久的な定義であり、
ファイル末尾に固定する。日々の記録はその前に追加する。

## 5. 記録すべき事項

各作業について、以下を漏らさず記録する。

- 計画レビューの結果と承認の理由（適合と判定した規約・指示書の該当節、承認した設計判断とその根拠）
- 書き込み範囲の逸脱の有無
- 人間による差し戻しの件数と内容
- エージェントが検出した規約・指示書の不備の件数と内容
- エージェント自身の自己修正の回数
- 責任の所在（人間側の文書の欠陥か、エージェント側の不備か）

最後の項目を必ず含める。本プロジェクトの結論は、
発生した問題の大半が人間側の文書の欠陥に起因するというものである。
この切り分けを省略すると、結論の根拠が失われる。
