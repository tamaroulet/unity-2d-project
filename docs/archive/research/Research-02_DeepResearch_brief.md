# 依頼：AIエージェントによる個人ゲーム開発ワークフローの網羅的調査

あなたは「AI支援ソフトウェア開発の方法論」を専門とする調査アナリストです。
以下の**実在するプロジェクトの失敗事例**を前提に、再発防止と立て直しのための
実証的・具体的・出典付きの調査レポートを作成してください。

## 0. 依頼者の状況（これが調査の文脈です。一般論ではなくこの状況への回答を求めます）

- **体制**: 個人開発者1名 ＋ AIエージェント2体
  - Claude Code（設計・アーキテクチャ・レビュー担当。有料枠のためレート制限があり、断続的にしか稼働できない）
  - Antigravity / Gemini（実装担当。ほぼ無制限に常時稼働可能。Unity-MCP でエディタを直接操作できる）
- **対象**: Unity 6 (6000.3.x) / C# / 2D / WebGL 出力の小規模ローグライク育成シミュレーション
  （24ターン、コマンド3種、ステータス3種、ボス4体、1プレイ3〜5分）
- **経過**: 約34時間（実働2日）
- **成果物の実測値**:
  - C# 8,911行 / 77ファイル / 12アセンブリ
  - EditMode 単体テスト 127件、全て合格
  - **PlayMode テスト 0件、CI のテストゲート 0件**
  - Git コミット 121件（内訳: `docs:` 40件 ＞ `feat:` 25件 ＞ `fix:` 14件）
- **実際に発生した失敗（すべて実測で確認済み）**:
  1. プロジェクト開始から **32時間** 経過するまで、画面（UIシーン）が一度も存在せず、
     一度も実行（Play）されなかった。Core→Command→Event→Ending→GameFlow→Relic→Boss→Meta
     という**ボトムアップのレイヤー積み上げ**で進行した。
  2. 初めて実行した直後、**89分間で16件の連続 `fix:` コミット**が発生。
     内容は全て結合層（シーン参照の欠落、UIが描画されない、フォント文字化け、
     ScriptableObject が null、ターン判定の誤発火、ダイアログが表示されない）。
     127件の単体テストはこれらを**1件も検出できなかった**。
  3. 修正が対症療法化した。具体的には
     (a) 依存解決処理を丸ごと `#if UNITY_EDITOR` で囲み `AssetDatabase.LoadAssetAtPath` で
     実行時に自己修復させた（＝**製品ビルドではその処理が消滅し再発する時限爆弾**）、
     (b) UIが壊れるたび `Update()` 内の `FindFirstObjectByType` と
     `transform.Find("文字列パス")` による再バインドを追加して症状を隠蔽した。
  4. 公開済みの WebGL ビルドは、16件の修正が入る**前**の版のままだった
     （＝人間が触れる環境が、常に実装より古く壊れている）。
  5. ゲーム概要書（設計ドキュメント）が、実装が全て終わった**後**に書かれた。
  6. AIへの統制を**自然言語のルールファイル（4ファイル・34KB）だけ**で行っていた。
     違反を検出・ブロックする機構（pre-commit フック、CIゲート）は一切存在しなかった。
     指摘を受けるたびにルールを追記したため、ルールが肥大化し遵守率が下がる悪循環に陥った。
- **人間（発注者）の評価**: 「2日かけて、ボタンを押すとターンが進むだけのものすら、
  自分の手で触れる状態になっていない」「自動開発と呼べる実態がない」

## 1. 調査の目的（この2点に答えることがゴール）

- **目的1**: 上記の失敗が、AIエージェント開発において**どの程度一般的な既知の失敗パターン**なのかを
  実例・言説・データで特定し、**成功している個人開発者が何を違えているのか**を具体的手順として抽出する。
- **目的2**: 本プロジェクトを**最短で「人間が触れるゲーム」に立て直す**ための、
  実行可能で検証済みの処方箋を得る。

## 2. 調査軸（A〜F すべてに回答すること。省略・統合は不可）

### 軸A: AIモデルの特性差とエージェント適性

- Claude（Opus / Sonnet 系）、Gemini（2.5 / 3 Pro 系）、GPT-5 / o シリーズ、
  および各社のエージェント製品（Claude Code / Antigravity / Codex / Cursor / Cline / Aider 等）について、
  **長時間の自律実行における挙動差**を、公開ベンチマークと実務者の一次証言の両方から比較せよ。特に：
  - 長いコンテキスト下での**指示の脱落率 / 指示追従性**（instruction following, context drift）
  - 「タスクを完了したと誤って宣言する」傾向（over-claiming / reward hacking）に関する報告
  - 自己判断で仕様を逸脱する傾向、逆に確認を求めすぎて停止する傾向
  - SWE-bench Verified / Terminal-Bench / METR の "task horizon"（自律作業可能時間）等の**定量指標**
- **「設計担当と実装担当を別モデルに分ける」構成（planner / executor 分離）は実務で有効か。**
  有効とする根拠、失敗するとする根拠の両方を、実例つきで示せ。
- **本件の構造的問題への評価**: レビュアー（Claude）にレート制限があり、
  実装者（Gemini）が無制限という**非対称な体制**は成立するのか。
  成立させるための具体的パターン（レビューのバッチ化、非同期レビュー、
  安価モデルによる一次レビュー、ゲート箇所の限定など）を調べよ。

### 軸B: プロンプト統制の限界と、決定論的オーケストレーション

- **ルールファイル（CLAUDE.md / AGENTS.md / .cursorrules / system prompt）の実効性の限界**について、
  実測・実験・実務者の証言を集めよ。
  「ルールが長いほど守られなくなる」現象に関する定量的知見があれば必ず含めること。
  推奨される最大分量、記述形式（宣言的 vs 手続き的）、階層化の作法。
- **プロンプトではなく機構でAIを縛る手法**を、具体的な設定例とともに網羅せよ：
  - Claude Code hooks（PreToolUse / PostToolUse / Stop）による強制実行とブロック
  - git pre-commit / pre-push フック、husky、lefthook
  - CI（GitHub Actions）による**マージ・デプロイの物理ブロック**（required status checks, branch protection）
  - lint / formatter / 型チェック / テストの必須化
  - サンドボックス・権限制御（許可ツールのホワイトリスト、書き込み可能パスの限定）
  - 「AIに絶対に触らせないファイル」を定義する手法（CODEOWNERS, .aiignore 等）
- **エージェントの逸脱を検出する手法**: 差分サイズの上限、コミット粒度の強制、
  変更ファイル数のガード、テストカバレッジ低下時の自動 reject など。
- **「AIに自己申告させる進捗（STATUS.md 等）は信用できるか」** —— 
  自己申告に頼らない、**機械的に検証可能な進捗指標**の作り方。
- **Unity 固有**: Unity プロジェクトで CI を回す実務手法（GameCI、Unity Test Runner の
  CLI 実行 `-runTests -testPlatform PlayMode`、ライセンス認証、ヘッドレスビルド、
  WebGL の自動ビルド＆自動デプロイ）を、**動作する設定ファイル例つき**で示せ。

### 軸C: 成功しているAI個人ゲーム開発の具体的ワークフロー

- **「最初の数時間で画面が触れる状態になる」ための具体的手順**を、
  実在の個人開発者・スタジオの記事 / 動画 / リポジトリから抽出せよ。
  抽象論ではなく、**時系列の手順（0〜1時間で何を、1〜3時間で何を、初日終了時点で何が動くか）**
  として再構成すること。
- AIエージェントに Unity を触らせる際の実務パターン：
  - シーンを AI に組ませるべきか、人間がテンプレートを用意すべきか
  - プレハブ / シリアライズ参照を AI に扱わせる際の事故（本件で発生した参照欠落）の**定番回避策**
    ——`Resources.Load` / Addressables / DIコンテナ (VContainer, Zenject) /
    ScriptableObject の直接参照 / コードによるシーン構築 —— の**比較と推奨**
  - Unity-MCP / Unity MCP Bridge 系ツールの実力と既知の落とし穴
  - Unity 以外の選択肢（Godot、Web/TypeScript+Phaser、LÖVE 等）が
    **AIエージェント開発に対して有利かどうか**の客観比較。
    特に「AIが結果を自分で目視・検証できるか（スクリーンショット取得、ヘッドレス実行の容易さ、
    シーンがテキスト形式か）」の観点を重視すること。
- **AIエージェントに「自分で動作確認させる」手法**：
  自動スクリーンショット、ヘッドレス実行、ログの自動回収、
  画像をLLMに読ませる視覚的検証ループ、Playwright 等によるブラウザ操作（WebGLビルドに対して）。
  実装例・リポジトリを挙げること。
- 情報源には必ず以下を含めること: 個人開発者のポストモーテム、
  Hacker News / Reddit (r/gamedev, r/Unity3D, r/ClaudeAI) の議論、
  GDC 講演、Anthropic / Google / OpenAI 公式のエージェント設計ガイド、
  実際に AI で完成・公開されたゲームのリポジトリ。

### 軸D: 「Vertical Slice First」vs「TDD / ボトムアップ先行」の失敗パターン

- ゲーム開発における **Vertical Slice / Playable First / Graybox** の定義と実務での位置づけ、
  「いつ作るべきか」「何を含めるべきか」を一次資料で示せ。
- **ゲーム開発でTDDが有効な領域と、有害になる領域**を切り分けよ。
  （純粋ロジック・数値バランス vs 描画・入力・シーン結合・体感）
  ゲーム業界でTDDが定着しなかった理由に関する議論を収集すること。
- **本件の核心**: 「単体テスト127件が緑なのに、動くゲームが存在しない」という状態を
  何と呼ぶか（例: 統合欠落、テストピラミッドの誤用、偽の安心感）。
  同種の失敗事例を**実例で3件以上**挙げよ。
- **Walking Skeleton**（Alistair Cockburn）、**Tracer Bullet Development**（Pragmatic Programmer）、
  **Steel Thread** の各概念を整理し、本件にどう適用すべきか具体化せよ。
- テストピラミッド vs テストトロフィー論争を踏まえ、
  **AIエージェントに書かせるテストの理想的な配分**（単体 / 統合 / E2E・スモーク）を論じよ。
  特に「AIは単体テストを書きすぎる」傾向の有無と、その対処法。
- **早すぎる抽象化（premature abstraction）**について。
  本件では小規模ゲームに対し12アセンブリ・イベントチャネル・ScriptableObject注入を先行導入した。
  AI生成コードで過剰設計が発生しやすい理由と、その抑制手法を調べよ。

### 軸E: 人間側のインプット（何を人間が用意すべきか）

- AIエージェントに開発させる前に、**人間が必ず用意すべき成果物**を優先度つきで列挙せよ。
  それぞれについて **最適なフォーマット・分量・具体テンプレート**を示すこと：
  - **GDD（ゲームデザイン文書）**: 個人開発でのミニマル版は何ページ・何項目が適正か。
    **1枚GDD / One-Page Design Doc** の実テンプレートを複数収集すること。
  - **ワイヤーフレーム / 画面遷移図**: 手描きで良いのか。AIに読ませる際の最適形式
    （画像 / ASCII図 / Mermaid / 構造化テキスト）はどれか。**実験的比較があれば優先。**
  - **完了の定義（Definition of Done）**とテスト観点の事前提示
  - **初期テンプレート**（Unityプロジェクトのスケルトン、シーン、CI設定）を
    人間が先に用意することの効果
  - **「作らないもの（Non-Goals）」**を明示することの効果
- **仕様の粒度問題**: 指示が粗すぎるとAIが勝手に決め、細かすぎると人間が全部書くことになる。
  **最適な粒度**についての実務的指針を収集せよ。
- 人間のレビュー頻度・チェックポイント設計（何時間ごとに、何を見るべきか）。
  「AIに任せて放置してよい範囲」と「必ず人間が目視すべき瞬間」の切り分け。

### 軸F: 本プロジェクトの立て直し処方箋

上記A〜Eを踏まえ、**この具体的プロジェクトに対する実行計画**を提示せよ。

- **48時間以内に「人間が触れるゲーム」に到達するための時系列タスクリスト**
  （何を捨て、何を残し、何を作り直すか。既存8,911行のうち何を破棄すべきかの判断基準も含む）
- **既存の技術的負債への具体的対処**:
  - `#if UNITY_EDITOR` 内の `AssetDatabase.LoadAssetAtPath` による実行時依存解決を
    どう置き換えるべきか（Resources / Addressables / DI / シーン直参照の比較と推奨）
  - `Update()` 内 `FindFirstObjectByType` と `transform.Find(文字列)` による
    UI再バインドの正しい代替
  - 12アセンブリ構成は維持すべきか、統合すべきか
- **導入すべき最小のCI / ゲート構成**（実際に動く GitHub Actions ワークフロー YAML を提示）:
  - PlayMode スモークテスト（シーンロード→ボタン押下→ターン加算→例外ゼロ）の実装例
  - テスト失敗時に main への push / Pages へのデプロイをブロックする設定
  - WebGL ビルドの自動化（人間が常に最新版を触れる状態の担保）
- **Claude / Gemini の役割分担の再設計案**（レビュアーがボトルネックにならない体制）
- **AIエージェントの逸脱を機械的に防ぐ具体設定**（hooks / gitフック / 権限設定の実ファイル例）
- **今後の完了定義（DoD）テンプレート**

## 3. 出力要件（厳守）

1. **形式**: 日本語。見出し付きの構造化レポート。軸A〜Fを章立てし、章ごとに
   「結論（3行）」→「根拠と実例」→「本プロジェクトへの適用」の3ブロックで書くこと。
2. **出典**: すべての主張に出典URLを付すこと。出典は以下を優先：
   - 公式ドキュメント（Anthropic / Google / OpenAI / Unity / GitHub）
   - 一次証言（開発者本人のブログ、GitHubリポジトリ、講演）
   - 定量データ（ベンチマーク、実験結果）
   **英語圏の情報源を必ず含めること**（日本語記事だけで完結させない）。
3. **禁止事項**:
   - 「一般的には〜が良いとされる」で終わる抽象論
   - 出典のない断定
   - 本プロジェクトの状況を無視した汎用アドバイス
4. **必須の添付成果物**（レポート末尾に付すこと）:
   - (a) **1枚GDDテンプレート**（そのまま埋められる形式）
   - (b) **Unity + GameCI の GitHub Actions ワークフロー YAML**
     （EditMode / PlayMode テスト ＋ WebGLビルド ＋ Pagesデプロイ、テスト失敗でブロック）
   - (c) **PlayMode スモークテストの C# サンプルコード**
   - (d) **AIエージェント用ルールファイルの推奨最小構成**（分量の目安と項目、悪い例と良い例）
   - (e) **48時間立て直し計画のタスクリスト**（時間割つき）
5. **分量**: 制限を設けない。ただし冗長な前置きは不要。密度を優先すること。
6. **相反する見解がある論点**（例: TDDの是非、Unity vs Godot、planner/executor分離の有効性）は
   **両論を併記し、どちらの条件下でどちらが妥当かを明示**すること。単一の推しに寄せないこと。
