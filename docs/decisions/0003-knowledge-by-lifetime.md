# ドキュメントを内容ではなく「寿命」で分類し、法則だけを蓄積する

## 決定日
2026-09-05

## ステータス
採用（2026-09-05。指示書 27 / cycle 2026-09-05-07 で実施完了）

## 背景

`docs/` の実測。

```
使い捨て（instructions 24 + handoff 30）   54 files   6,642 行
research（生資料）                         18 files   5,158 行
log.md（追記型の日記）                                1,243 行
spec / strategy / nightly / archive                   1,714 行
──────────────────────────────────────────────────────────────
decisions/（永続的な知識）                  4 files     328 行  ← 全体の 2%
```

**ランタイム C# が 3,785 行に対し、docs は約 15,000 行。製品の 4 倍ある。**
そのうち次のゲームに持っていける知識は 328 行しかない。

### 決定的な実例

指示書 **18・19・23 は、すべて同じ型のバグを直している。**
「非アクティブなパネルに View が乗り `OnEnable` が走らない」（`BossBattleDialogView` /
`MetaShopDialogView` / `EventDialogView`）。

3 枚で約 600 行。**フォルダは 3 ファイル増え、知識は 0 のまま増えなかった。**
知識になったのは指示書 26 で `INV-3` を書いた瞬間であり、それは **3 行**である。

```
600 行の使い捨て  →  3 行の法則
```

現在の構造には、この圧縮を起こす機構が存在しない。だから同じ失敗に 3 回書いた。

## 決定内容

### 1. 分類の軸を「内容」から「寿命」へ変える

```
docs/
  laws/            【永続・次ゲームへ持ち出す】
    invariants.md      不変条件と、それぞれが塞いだ過去のバグを 1 行ずつ
    failure-modes.md   失敗の型カタログ（症状 → 法則 → 検出手段）
  decisions/       【永続】ADR
  spec/            【プロジェクト限り】このゲームの仕様
  STATUS.md        【プロジェクト限り】現在地 1 枚。上書きのみ
  cycles/          【使い捨て】1 サイクル 1 フォルダ（指示書 + 02-context + 04-result + 05-review）
  archive/         完了サイクルの墓場
```

`instructions/` と `handoff/` を **`cycles/` に統合する。**
現在は 1 サイクルが 2 箇所に分かれており、追うのに両方を読む必要がある。

### 2. 複利を生む機構を 1 つ置く

> **サイクルを閉じるとき、必ず問う。「これは法則になるか?」**
> なるなら `laws/` に数行足す。ならないなら `cycles/` をアーカイブして忘れる。

判定基準を明文化する。

> **同じ型のバグに 2 枚目の指示書を書いたら、それは知識化の失敗である。**

この問いは `05-review.md` の必須項目とする。レビューの最後に
「本サイクルから `laws/` へ足すもの: あり（内容） / なし」を書く。

### 3. `laws/` に上限を設ける

**合計 150 行以内。** `.agents/rules/00_rules.md`（`trigger: always_on`）と同じ扱いができる大きさに保つ。

**溢れたら足すのではなく統合する。** 法則が 20 本を超えたら細かすぎるということなので、
上位の法則にまとめ直す。**小さく保つという制約が、知識の質を強制する。**

### 4. 追記型を全廃する

| 対象 | 処置 |
|---|---|
| `docs/log.md`（1,243 行の日記） | **廃止。** `STATUS.md` への上書きに寄せる |
| `docs/nightly/` | CI の成果物とし、`logs/` と同様に追跡外へ |
| `docs/PLAN_ROADMAP.md` | `STATUS.md` に統合 |
| `docs/research/`（5,158 行） | 結論を `decisions/` か `laws/` に吸わせ、生資料は `archive/` へ |

**増え続けてよいのは `laws/` だけ。それにも上限がある。**

### 5. 次のゲームへの持ち出し集合を定義する

```
laws/  +  decisions/  +  .agents/rules/00_rules.md  +  scripts/  +  Game.Core（Brain 層）
```

**これだけをコピーすれば、次のゲームは 1 日目から不変条件と機械判定を持って始まる。**

`cycles/` と `spec/` は持ち出さない。前のゲームの都合が、新しいゲームの制約になる。

### 6. Architect の読み取り範囲を更新する

`00_rules.md`「セッション枠」の 3 ファイル制限に `laws/` を加える。
`laws/` は 150 行以内なので、常時読んでも負担にならない。

## 検討した代替案

### 案 A: 現状維持（内容で分類し、全部残す）

**却下。** 15,000 行のうち 98% が次に効かない。しかもサイクルごとに約 5 ファイル増える。
Architect の読み取りを 3 ファイルに制限したのは、この増加への対症療法だった。**上流で止める。**

### 案 B: 全部消して `laws/` だけにする

**却下。** ADR と spec は消せない。また、進行中サイクルの `04-result.md` は
レビューの入力として必要である。**寿命ごとに扱いを変えるのが正しく、一律の削除ではない。**

### 案 C: 検索やインデックスで大きさに対処する

**却下。** 情報が増えることを前提にした対策であり、
「作るほど次が速くなる」という目的に反する。**量を減らすことが目的である。**

## 結果と影響

### 得られるもの

- **次のゲームの初日が変わる。** 持ち出し集合だけで、不変条件・機械判定・規約が揃った状態から始まる
- Architect が読む量が構造的に減る（`laws/` は 150 行以内）
- 同じ型のバグに 2 度目を書いたことが**検出可能になる**（`laws/` を見れば分かる）
- サイクルごとの増加が `cycles/` に閉じ込められ、アーカイブで切り離せる

### 代償

- **移行作業が発生する。** 54 ファイルの `git mv` と、リンクの張り替え
- 過去の指示書へのリンクが切れる。ADR や規約からの参照は書き換えが必要
- `laws/` の 150 行上限は、いずれ必ず窮屈になる。**そのとき統合する運用が回るかは未検証である**

### 段階

1. `laws/` を新設し、指示書 26 の INV-1〜6 を `invariants.md` に写す（**先に器を作る**）
2. `failure-modes.md` に、過去に起きた失敗の型を書く（同一パネル罠 / 報告の捏造 / 枠枯渇時の越権など）
3. `instructions/` と `handoff/` を `cycles/` へ統合する
4. `log.md` / `PLAN_ROADMAP.md` / `nightly/` を整理する
5. `research/` の結論を吸い上げ、生資料を `archive/` へ
6. `00_rules.md` に §2 の問いと §6 の読み取り範囲を追記する

**1 と 2 を先に行う。** 器と中身が無いまま移動だけしても、複利は始まらない。

### 実施しない範囲

- `docs/webgl/` 13MB の扱い（配信元の確認が先）
- `Game/Assets/` 側のファイル構成
- 実施は指示書 27 で行う。本 ADR は方針のみ
