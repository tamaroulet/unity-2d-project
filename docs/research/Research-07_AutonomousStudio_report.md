## 1. 対立点の裁定 — Godot

2 本のレポートが正面から食い違った。

| | レポート 1 | レポート 2 |
|---|---|---|
| M2 テキスト所有率 | 99% | 70〜80% |
| 人間の GUI 必須箇所 | 実質なし（MCP 経由） | UUID 破損時に GUI での保存修復が必要 |
| ヘッドレス CI | 容易 | `.blend` インポートでハング、1 時間タイムアウト |
| マージ | API 経由で回避可能 | `.tscn` 競合でコミット履歴が消失した実例 |

**レポート 2 を採る。** 故障の機序が具体的（`uid://` の不整合 → `res://` へのフォールバック → 無効参照）であるのに対し、
レポート 1 の「MCP が 2026 年に確立済み」は機序も出典もない。

### レポート 1 が正しくても、Godot の優位性にはならない

レポート 1 の核心は「AI がエディタ API を直接叩いて生きた状態を改変すれば高効率」である。

**それはこの現場が既にやっていることである。**

```
UILayoutBuilder.cs   SerializedObject / FindProperty でシーンを構築・結線している
MetaProgressionSceneBinder.cs / BossSceneBinder.cs / RelicSceneBinder.cs  同様
```

そして**それでも未バインドが 3 サイクル連続で再発した**（`MetaShopDialogView` / `BossBattleDialogView` /
`EventDialogView`、いずれも「非アクティブなパネルに View が乗り `OnEnable` が走らない」同型）。

**「エディタ API へのアクセスがあれば自律開発は高効率で回る」は、この現場の実測が反証している。**
したがって、それを根拠に 6 週間級（レポート 1 が挙げた Bevy→Unity 移植の実測値）の移行を行う理由がない。

## 2. 仮説 H1 の修正

> 旧 H1: 効率は「AI が直接読み書きできるテキスト」の割合でほぼ決まる

**棄却。** 2 本とも同じ方向に修正しており、この現場の実測とも一致する。

> **新 H1: 効率は、ゲームの状態と規則が、描画層から分離された純粋なコードとして
> 表現されている割合で決まる。ファイル形式がテキストかどうかは二次的である。**

根拠。Unity の `.unity` はテキストだが、GUID と fileID の網であり AI には安全に編集できない。
Godot の `.tscn` もテキストだが、`uid://` の不整合で同様に壊れる。
**テキストであることは条件を満たさない。** 分離されていることが条件である。

この修正により、`docs/decisions/0001-brain-body-separation.md` の位置づけが強化される。
あれは「Unity を生き延びる」策ではなく、**支配要因そのものに手を入れる策**である。

## 3. M5（出荷可能性）— 解決済み

調査で最大の発見は、M5 が「開示義務」ではなく「**権利**」の問題だったことである。

- Steam はトレーニングデータの権利を積極的に証明できない場合に配信を拒否する。
  `DREAMIO` は実際に拒否され、開発者はプロジェクトを放棄した
- 純粋な AI 生成物には著作権が発生しない（Allen v. U.S. Copyright Office / USCO 2025-03 ガイダンス）。
  **競合が合法的に複製できる**
- itch.io のジャムは生成 AI を全面禁止する方向にある

**人間がアセットを制作するという決定により、上記はすべて該当しなくなった。**

Steam はコードへの AI 利用（開発効率化ツール）を開示不要と明記している。
したがって次の線が引かれる。

| | 制作者 | 根拠 |
|---|---|---|
| **コード・システム・テスト・ツール** | AI が 100% | Steam の開示対象外。著作権上の争点にならない |
| **プレイヤーが直接消費するアセット** | **人間** | 著作権が発生し、権利証明が可能になる |

副次的に、Web/TS スタックの最大の利点（ストア審査の回避）の価値が下がり、
**エンジン選定は Unity 継続で確定した。**

### 現状の追認

```
ProceduralSpriteGenerator.cs   Texture2D に SetPixels で幾何形状を描画
拡散モデル由来の画像            0 枚（png 24 枚はスクリーンショットのみ）
```

現行アセットはコード生成であり、権利上クリーンである。
ただしこれは**最終形ではなく仮アート**として扱う。人間の制作物に差し替わる前提の足場である。

## 4. M1 の定義を分割する

ブリーフの M1「人間の手作業 15 分以内」は誤っていた。**敵は人間の関与ではなく、人間の機械的作業である。**

| | 扱い | 目標 |
|---|---|---|
| **創作時間**（アセット制作・見た目と手触りの判断） | 価値そのもの | **制限しない** |
| **作業時間**（結線・デバッグ・確認のための手動操作） | 純粋な損失 | **ゼロに近づける** |

この定義で見ると、残る構造的欠陥は **Inspector 結線ただ 1 つ**である。
「人が触れるところ」ではないのに人間の手作業が必須で、3 サイクル連続で壊れた唯一の場所である。

**→ `docs/decisions/0002-code-first-bootstrap.md` で扱う。**

## 5. ローカル AI の導入判定

レポートは VLM と SLM ワーカーの導入を提案している。**個別に判定する。**

| 用途 | 判定 | 理由 |
|---|---|---|
| **ログ・テスト XML の解析** | **却下** | 決定的にできる。NUnit XML も MSBuild 出力も構造化済みで、`mechanical_check.ps1` が既にパースしている。**決定的にできることに AI を挟まない** |
| **コンパイルエラーの自動修正** | **却下** | `00_rules.md`「対症療法の禁止」に正面から抵触する。エラー箇所に機械的なパッチを当てる装置になる |
| **マージ競合の自動解決** | **却下** | 実装エージェントが 1 体・直列であり、競合が発生していない。存在しない問題への対策 |
| **VLM による視覚検証**（文字化け・UI 重なり） | **条件付きで検討** | 決定的手段で到達できない唯一の領域。ただし §5-1 の前提を満たしてから |

### 5-1. VLM を入れるための前提

VLM 導入は**基盤構造に影響する**ため、先に条件を確定させる。

**① 決定性 — 既に満たしている**

```
$ grep -rn "Random" Game/Assets/Features Game/Assets/Core --include=*.cs
（0 件）
```

**ランタイムに乱数が 1 つも無い。** ランダム性はモンテカルロテストが外から注入している
（`GameMonteCarloSimulationTests.cs:62` の `new System.Random(42)` 等）。
**同じ入力列は必ず同じ画面になる。** シード注入の実装は不要である。

**② 任意の画面を単独で描画できること — ADR 0002 が前提**

Code-first Bootstrap により UI がコードから構築されるようになれば、
ターン 24 まで遊ばずに「ショップ画面だけ」を直接構築してスクリーンショットを撮れる。
コンポーネント単位の視覚回帰検査になる。

**現状は `ScreenCapture` の呼び出しが 1 箇所も無い。** 撮影機構自体が未実装である。

**判定: VLM は ADR 0002 の完了後に検討する。単独では導入しない。**
先に入れると「ターン 24 まで遊んでから撮る」形になり、1 枚のスクショに数分かかる装置になる。

## 6. 無人実行の判定

AutoRunner は 2026-09-05 04:30 に起動し、30 分かけて `exit=1` で終わり、成果は 0 だった。
指示書 1 枚を `auto/wip` に巻き込んだだけである。

**失敗の構造は「判断する AI を無人で回した」ことにある。** 実行基盤の問題ではない。

### 原則

> **無人で回してよいのは決定的処理のみ。判断を伴う工程を無人で回さない。**

| 無人でよい | 無人にしない |
|---|---|
| ビルド / テスト / スナップショット生成 / 機械判定 | 実装（設計判断を含む） |
| モンテカルロ / WebGL ビルド / デプロイ | レビュー / 裁定 |
| （将来）スクリーンショット撮影 | 指示書の解釈 |

### 置き場所

**ローカルのスケジュールタスクではなく GitHub Actions に置く。**

```
.github/workflows/   unity-test.yml / webgl-build.yml / deploy_pages.yml / unity-activation.yml
main は origin より 64 コミット ahead
```

**CI は構築済みで、push していないため一度も動いていない。** 無料枠で、ローカル PC を占有せず、
決定的処理だけを回す枠として要件に完全に一致する。

**判定: AutoRunner（無人の実装エージェント）は復活させない。無人枠は CI に移す。**
移行の前提は push であり、それは ADR 0002 でシーンが軽くなってからでよい。

---

## 7. 基盤構造への反映（このレポートが確定させたこと）

1. **エンジンは Unity 継続。** 移行を検討しない
2. **H1 を修正。** ADR 0001（Brain 切り出し）は支配要因への直接の手当てとして維持
3. **ADR 0002（Code-first Bootstrap）を起草する。** 残る唯一の構造的欠陥への手当て
4. **アセットは人間が作る。** 生成パイプライン（Asset-as-Code）を計画から削除する
5. **SLM ワーカーは導入しない。** VLM は ADR 0002 完了後に再検討
6. **無人実行は CI へ。** AutoRunner は復活させない
7. **`docs/strategy/AUTONOMOUS_STUDIO_TARGET.md` を v2 へ改訂する**
