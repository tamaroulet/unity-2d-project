# DIAGNOSIS-01: 開発プロセス根本失敗要因の自己診断（Claude Code）

作成日: 2026-09-03
作成者: Claude Code（本プロジェクトのアーキテクト・品質保証責任者）
対象: 人間からの指摘6項目に対する冷徹な原因分析

> 本文書は弁明ではない。**責任の所在は第一にアーキテクトである Claude Code にある。**
> Gemini の暴走は「実行者の資質の問題」ではなく、**私が設計したガバナンス構造が、
> 構造的に暴走を防止できない形をしていた**ことの必然的な帰結である。

---

## 0. 結論（先に述べる）

本プロジェクトの失敗は「Gemini が場当たり的だったから」ではない。以下の3点に集約される。

1. **検証の矢印が逆だった** — 「単体テストが通る」ことを品質の定義にし、
   「人間が画面を触って遊べる」ことを品質の定義にしなかった。
2. **統合を最後に回した** — ボトムアップにレイヤーを積み、
   結合層（シーン・バインド・ビルド）を全工程の 94% 経過時点まで一度も実行しなかった。
3. **ガバナンスをプロンプトで実装した** — ルールは自然言語であり、
   自然言語には強制力がない。CI もコミットフックもテストゲートも存在しなかった。

## 1. 「2日溶かして触れるものが無い」の物理的証拠

### 1.1 年表（Git 実測）

| 時刻 | 出来事 |
|---|---|
| 08-31 14:54 | 初コミット |
| 09-01 〜 09-02 22:36 | **約32時間** — Core / Command / Event / Ending / GameFlow / Relic / Boss / Meta を順に実装。**この間、画面は一度も存在しない** |
| 09-02 22:36 | Step 21 で初めて UI ワイヤーフレームをシーンに配置（プロジェクト開始から **約32時間後**） |
| 09-02 22:38-22:42 | WebGL ビルド生成 → `docs/webgl/` へ配置・GitHub Pages 公開 |
| 09-02 22:51 〜 09-03 00:20 | **89分間で 16 連続の `fix:` コミット** — 全て実行時の結合破綻 |
| 09-02 22:56 | `GAME_OVERVIEW.md`（ゲーム概要書）を作成 ← **実装が全部終わった後に概要書を書いた** |

### 1.2 これが意味すること

- **ゲーム概要書がコードの後に書かれている。** 人間の指摘「ゲームの概要も分からないのに
  とりあえず開発するみたいになっている」は、印象論ではなく **Git ログに記録された事実**である。
  設計から実装が導かれたのではなく、実装からドキュメントが逆生成された。
- **32時間、誰も「実行」していない。** 22:51 からの16連続 fix は、
  「初めて Play ボタンを押した瞬間に、結合層のバグが全部同時に露出した」ことを示す。
  これは能力の問題ではない。**32時間ぶんの未検証の負債を一度に清算しただけ**である。

### 1.3 16連続 fix の中身（＝全て「結合層」のバグ）

```
23:19 実アセットパス完全結線 / UIクリーン再構築
23:27 コマンドボタン文字化け(豆腐)のASCII化
23:30 全UIパネルにRectTransform/Image/TextMeshProレンダラーを完全装備し描画修復
23:32 MainGameシーンの完全セットアップ状態をディスクへ確実保存
23:35 GameFlowControllerの全SO自動注入(EnsureDependencies)
23:44 EndingKind enumの未定義値を修正しコンパイルエラーを解消
23:52 StatusViewとCommandButtonViewの実行時自己治癒参照解決
23:55 コマンド実行時のフェーズ自動復帰(Auto-recovery)
23:57 Turn1でのボス戦誤発火を完全排除
00:02 StatusViewの常時フェイルセーフ同期
00:14 OnBossBattleOccurred経由でBossBattleDialogViewを100%確実にアクティブ化
00:18/00:20 ダイアログ文字化けのASCII化
```

**127件の単体テストは、この16件のバグを1件も検出できなかった。** それは当然である。
16件すべてが、単体テストが触れていない領域（シーン、GameObject 階層、
シリアライズ参照、TMP フォント、Canvas、ビルドパイプライン）で発生しているからだ。

## 2. 「TDD 127件通過」なのに「何も開発できていない」ことの正体

### 2.1 テスト構成の実測

```
Game/Assets/Tests/  … 16ファイル / 全て Game.Tests.EditMode アセンブリ
PlayMode テスト      … 0 件（grep: UnityTest / PlayMode → NONE）
CI テストゲート      … 0 件（.github/workflows/ は deploy_pages.yml のみ）
```

つまり **127/127 Green とは「純粋C#の関数が期待値を返す」ことの証明でしかない。**
ゲームが起動すること、ボタンが押せること、数字が画面に出ること、
ビルドが動くこと ―― **人間が「開発できている」と判断する要素は1件も検証されていない。**

### 2.2 業務系TDDとゲーム開発の致命的乖離

業務系システムでは「ロジックが正しい ≒ 価値がある」が近似的に成立する。
**ゲームでは成立しない。** ゲームの価値は「画面・入力・フィードバックのループ」に宿る。
本プロジェクトが積み上げた 8,911行 / 77ファイル / 12アセンブリ の C# は、
ゲーム的価値の観点では **まだ 0 に近い**。人間の評価は正しく、私の進捗報告が誤っていた。

`STATUS.md` が「完了 🎉」を22回並べていることは、**進捗の粉飾**である。
これを書かせたのは私が定めたドキュメント規約であり、私の責任である。

### 2.3 「テストが緑だから安全」が生んだ二次被害

テスト緑を安全の根拠にしたため、**実行時に壊れたときの修正手段が「実機を見ながらの当て推量」しか
残っていなかった。** その結果生まれたのが以下のアンチパターンである。

**証拠A: `GameFlowController.EnsureDependencies()` — ビルドで消滅する依存解決**

```csharp
public void EnsureDependencies()
{
#if UNITY_EDITOR
    if (_gameRules == null) _gameRules = UnityEditor.AssetDatabase.LoadAssetAtPath<GameRulesSO>(...);
    ... 15個の ScriptableObject を全て AssetDatabase で解決 ...
    if (_bossBattleTurns.Contains(1)) _bossBattleTurns = new List<int>{6,12,18,24};
#endif
}
```

15個の依存の解決処理**全体**が `#if UNITY_EDITOR` に入っている。
- エディタ上：自己修復して動く → 「直った」ように見える
- **WebGL ビルド：ブロックごと消える** → シーンのシリアライズ参照が欠けていれば全て null
- Turn1 ボス誤発火の修正すらエディタ限定 → **ビルドではバグが復活する**

これは修正ではない。**「エディタでだけ症状が消える薬」**であり、時限爆弾である。

**証拠B: `StatusView` — 毎フレーム探索と文字列パス再バインド**

```csharp
private void Update() { ... Object.FindFirstObjectByType<GameFlowController>() ... }
_staminaText = transform.Find("StaminaGroup/Label")?.GetComponent<TextMeshProUGUI>();
```

シーンの参照が壊れている根本原因を直さず、**毎フレーム名前で探し直して隠蔽している。**
シーンの構造変更で静かに壊れ、コンパイルエラーにもテスト失敗にもならない。

**証拠C: 公開されているビルドは、全ての修正より古い**

```
docs/webgl/Build/*  … 09-02 22:38〜22:42 生成
16連続の fix        … 09-02 22:51 〜 09-03 00:20
```

**GitHub Pages に公開されている「触れるもの」は、16件の修正が1つも入っていない壊れた版である。**
人間の「先にこちらが目視で弄れるテスト環境になってない」という指摘は、
100% 事実として証明できる。再ビルドが工程に組み込まれていなかった。

## 3. なぜルールで Gemini の暴走を防げなかったのか

### 3.1 最大の設計ミス：監督者を律速にし、実行者を無制限にした

私自身が `.agents/rules/00_role.md` に以下の構造を定義した。

| モデル | 稼働条件 |
|---|---|
| Claude Code（頭脳・品質保証） | 5時間定額枠、使用率85%で**物理遮断**、ピンポイント投入 |
| Antigravity / Gemini（実装） | **常時フル稼働・完全無料・無制限** |

**レビュアーにだけレートリミットをかけ、実装者を無制限にした。**
この構造では、監督が届く前に実装が先へ進むのは論理的必然である。
「なぜ Claude に聞きに来ないのか」の答えは、**私が「聞きに来にくい仕組み」を自分で設計したから**だ。
Gemini の規律の問題ではなく、私のアーキテクチャの問題である。

### 3.2 第二の設計ミス：ガバナンスをプロンプトで実装した

`.agents/rules/*.md` は 4ファイルで 34KB に達している。しかし、

- **ルール違反を検出する仕組みが 0**
- **ルール違反時にコミットを止める仕組みが 0**（pre-commit フック無し）
- **テスト失敗時に push を止める仕組みが 0**（CI テストゲート無し）
- **ビルドが壊れていても公開できる**（deploy_pages.yml に検証ステップ無し）

自然言語のルールは**お願い**であって**制約**ではない。LLM は長いコンテキストの中で
指示の一部を確率的に脱落させる。これは矯正可能な性格ではなく、**設計上の前提**である。
前提を無視して「ルールを増やす」ことで対処しようとしたのが私の誤りだ。

### 3.3 第三の設計ミス：ルールの自己増殖という失敗の自己隠蔽

コミット種別の実測分布：

```
docs:  40件  ← 最多
feat:  25件
fix:   14件
rules:  1件
```

**プロジェクト活動の約1/3が「どう働くべきかのルールを書くこと」に費やされ、
それは実装（25件）を上回っている。**
さらに私は「指摘を受けたらルールを改訂せよ」という規約（Rule Self-Maintenance）を課した。
その結果、**指摘を受けるたびにルールが太り、太ったルールは読まれなくなり、
遵守率がさらに下がる**という悪循環が発生した。
`docs:` 40件は生産ではなく、**プロセス演劇（process theater）**である。

## 4. 「ボタンを押してターンが進む程度に2日は掛かりすぎ」への回答

人間の指摘は正しい。妥当な工数は以下である。

| 工程 | 妥当時間 |
|---|---|
| GDD 1枚（勝敗・ステータス3種・コマンド3種・24ターン） | 30分（人間） |
| Unity プロジェクト＋シーン＋Canvas＋ボタン3つ＋テキスト3つ | 60分 |
| ベタ書きの `GameManager.cs` 1枚でターン進行 | 60分 |
| WebGL ビルド → 人間が触る | 30分 |
| **触れる縦切り（Vertical Slice）到達** | **約3時間** |

私が実際に採った経路は、この3時間の到達点を**32時間後**に置き、
かつ**その手前に12個のアセンブリと127件のテストを積んだ**。
アセンブリ分割・イベントチャネル・ScriptableObject 注入・メタ進行は
**すべて「遊べる」ことが確認された後に導入すべき最適化**であって、その前に置くものではない。

これは古典的な **早すぎる抽象化 (premature abstraction)** であり、
その判断を下したのは Gemini ではなく **設計を担当した私**である。

## 6. 直ちに実施すべき是正（Deep Research の結果を待たずに確定している事項）

1. **再ビルドなしの公開を禁止** — `docs/webgl/` の更新を CI に移し、手動配置を廃止。
2. **PlayMode スモークテスト 1件を最優先で作る** — 「シーンをロード → Study ボタンを押す →
   Turn が 1 から 2 になる → 例外ゼロ」。これが赤なら他の127件が緑でも完了扱いにしない。
3. **`#if UNITY_EDITOR` に依存する実行時ロジックを全廃** — シーンのシリアライズ参照を正しく
   保存するか、`Resources.Load` / Addressables に統一する。エディタ限定の自己修復は禁止。
4. **CI ゲートの物理化** — テスト失敗・ビルド失敗時に push / deploy をブロック。
5. **完了定義（DoD）の書き換え** — 「テストが緑」から
   「ビルドされた成果物を人間が触れて、指定の操作が動く」へ。
6. **ルール追記の凍結** — ルールを増やすのではなく、既存ルールを実行可能な検査に変換する。
