## 1. 調査目的

## 2. 業界動向（2025〜2026年）

### 2.1. Spec-Driven Development（SDD）

2025〜2026年にかけて、AI 支援開発は「コード補完」から
「エージェンティック・エンジニアリング」へ移行している。
最も効果的とされるアプローチは SDD（Spec-Driven Development）であり、
以下の原則に基づく:

- **設計（Planning）と実装（Coding）を分離する**:
  計画を立てるエージェントと実装するエージェントを区別し、
  実装中にシステム設計を変更させない
- **仕様書を共有の真実（Shared Source of Truth）とする**:
  `requirements.md`, `architecture.md` 等の永続ドキュメントを
  エージェントが参照する基盤とする
- **Human-on-the-Loop**: 開発者はアーキテクトおよびレビュアーとして
  機能し、AI 出力はすべて「ドラフト」として扱う

### 2.2. 上流→下流検証パイプライン

品質保証を独立した決定論的ゲートのパイプラインとして構造化する:

| フェーズ | アクション | 目的 |
|:---|:---|:---|
| **上流** | 仕様・ルールの確認、コンテキスト整備 | 意図の整合 |
| **計画** | タスク分解 | 明確でモジュール化された手順の定義 |
| **実装** | チケット・仕様に基づく実行 | アーキテクチャの逸脱防止 |
| **検証** | Lint → Test → Build | 決定論的ゲートによる品質保証 |
| **フィードバック** | 仕様・計画の修正 | 失敗時のループ閉鎖 |

### 2.3. ベストプラクティス

- **小さなバッチ**: 大きな機能を最小の作業単位に分解する。
  レビューが容易になり、リグレッション時のデバッグ範囲が最小化される
- **敵対的レビューループ**: マルチエージェント体制では、
  「検証者（Verifier）」エージェントが「実装者（Implementer）」の
  出力を検査する。問題発見時は実装者に差し戻す
- **強制ゲート**: エージェントの規律に依存しない。
  自動化された決定論的検証ゲートを設け、
  エージェントがバイパスできないようにする
- **CLAUDE.md（ルールファイル）の整備**: プロジェクト固有の
  コーディング規約・アーキテクチャ制約・禁止パターンを永続ファイルに
  記述し、セッション開始時にエージェントが必ず参照する

## 3. 本プロジェクトの既存ルールとのギャップ分析

### 3.1. 既に対応済みの領域

| ベストプラクティス | 本プロジェクトの対応 |
|:---|:---|
| SDD（仕様駆動） | `docs/spec/CodingSpec.md` の Living Spec 原則 |
| ルールファイル | `.agents/rules/` に 1 ファイル（統合済み） |
| 設計と実装の分離 | Claude（頭脳）と Gemini（手足）の 2 モデル体制 |

| 検証ゲート | `run_tests` 100% Green をコミット条件化 |
| 敵対的レビュー | Claude による監査・レビュー |

### 3.2. ギャップ（不足している領域）

| ギャップ | 詳細 |
|:---|:---|
| **修正時の上流確認が未強制** | 6 段階ワークフローは「新規機能実装」を前提としており、既存コードの修正・バグ修正時の手順が規定されていなかった。そのため「エラーを見たらすぐ修正」という場当たり的行動が繰り返された |
| **修正後の下流検証の曖昧さ** | コミット前の 100% Green は規定されているが、「修正が元の問題を解決したか」「新たな問題が発生していないか」の確認手順が明文化されていなかった |
| **修正計画の欠如** | 修正前に「何をどう直すか」を明文化するステップがなく、複数ファイルへの変更が散発的に行われた |

## 4. 改善策

上記ギャップを埋めるため、4 段階ゲートは散文規約としては廃止し、`nightly_gate.py` の判定コードへ移した。
