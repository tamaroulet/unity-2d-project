## 0. この文書の使い方

**擦り合わせの単位は「主張」ではなく「実測値」とする。**

外部研究は一般論として正しくても、この現場の数字と食い違うことがある（§4 で 2 件出た）。
本書は次の順で更新する。

1. 実測を取る（`mechanical_check.ps1` / スナップショット / 枠の消費率）
2. 実測が本書の前提を否定したら、本書を直す。研究や好みで直さない
3. 争点が出たら `docs/decisions/` に ADR を 1 枚起こす。本書は結論だけを持つ

## 2. 実測ベースライン（2026-09-05 時点）

### コード規模

```
ランタイム C#      3,785 行
Editor スクリプト  2,643 行
テスト             4,129 行
docs/              60 ファイル超
MainGame.unity     340,969 bytes ≈ 106,552 トークン
```

**プロセス（docs）が製品（ランタイム 3,785 行）より重い。** これが目標 2 の主因である。

### 時間

```
EditMode  116 件 / 0.88 秒          ← Unity 起動を含まない純粋計算
PlayMode    3 件 / Unity 起動込み    ← 分単位
2026-09-05 04:30  agy が PlayMode 系タスクに 30 分かけて exit=1
```

**Unity の起動が唯一のボトルネックである。** 目標 3 はここを迂回しない限り達成しない。

### 枠

```
対話 1 セッションで 15 分あたり 5 時間枠の約 6%
週間枠 51%（9/5 時点）
使用量の 79% が 150k 超のコンテキストで発生
--resume によるセッション再利用は動作確認済み（7d0f3a0）
```

**消費の主因はモデル単価ではなく「読む量」だった。** シーン 1 回の読み込みが 10.6 万トークン、
1 監査で 15 ファイル。これを規約で塞いだ（`0546e3c` / `cd3132f`）のが最も効いた。

### 故障の型（3 サイクル連続で同じもの）

```
MetaShopDialogView   非アクティブなパネルに View が乗り OnEnable が走らない
BossBattleDialogView 同型（指示書 18）
EventDialogView      同型（指示書 23）
未バインドの残件      15 件
```

**この現場の故障は YAML マージ競合ではない。「結線が見えないこと」である。** §4 で効く。

## 3. 目標アーキテクチャ

外部研究の "Brain-Body Separation" を採用する。ただし役割の割り当てはこの現場に合わせる。

```
┌─ Orchestrator ── Claude Opus ─────────────────────────────┐
│  設計判断・指示書の発行・レビュー・裁定                    │
│  読むのは 02-context.md / 指示書 / 04-result.md の 3 つだけ │
└───────────────────────────────────────────────────────────┘
        │ 指示書（1 枚 = 1 機能）
        ▼
┌─ Brain ── Pure C#（UnityEngine 非依存）───────────────────┐
│  ルール・状態遷移・数理・セーブ形式                        │
│  検証は dotnet test。**Unity を起動しない**                │
│  → 安価な実装 AI が並列で触ってよい層                      │
└───────────────────────────────────────────────────────────┘
        │ データ（GameState / 結果 record）
        ▼
┌─ Body ── Unity（View と結線）─────────────────────────────┐
│  描画・入力・シーン・SerializeField                        │
│  **同時に 1 エージェントのみ（直列）**                     │
│  検証は PlayMode ＋ 人間の目視                             │
└───────────────────────────────────────────────────────────┘
        │
    人間: 方向づけ / アセット配置 / 目視確認
```

**並列化は Brain 層でのみ行う。** Body を並列化しない。Unity 起動が重く、
シーンは 1 つしかなく、競合させる意味が無い。

## 4. 外部研究との突き合わせ — 採否

### 採る

| 研究の主張 | 採用理由 | 現状 |
|---|---|---|
| **Brain-Body Separation（Pure .NET 分離）** | Unity 起動がボトルネックという実測に直接効く。最優先 | 未着手。§5 |
| **Prompt Caching / セッション再利用** | 定額枠でも効く。実測で確認済み | **実装済み**（`--resume`, 7d0f3a0） |
| **Agentic Guardrails（pre-commit / 保護ファイル）** | 指示書外のファイル改変が実際に起きた（`6ca2450`） | 部分実装（`guard.js` + 保護リスト） |
| **レートリミット対応のオーケストレータ** | 枠枯渇が実際に規約違反を誘発した | **実装済み**（`invoke_claude_safe.ps1` 85% 遮断） |
| **LLEA によるバランス自動調整** | モンテカルロ基盤が既にある | 部分実装（`GameMonteCarloSimulationTests`） |
| **決定性（同じ入力＝同じ画面）** | VLM 検証と再現可能なバグ報告の前提 | **既に達成。** `Features`/`Core` に乱数が 0 件 |

### 採らない — 実測が前提を否定している

**① 「定額サブスクを解約して API 従量課金へピボットせよ」（10k_research）**

否定する。根拠は 3 つ。

- 研究の前提「定額枠では自律ループが数十分で止まる」は正しいが、**止まった原因は単価ではなく読む量だった。** シーン読み込み禁止と Architect の読み取り 3 ファイル制限で、同じ枠のまま消費が桁で変わった
- `--resume` によるセッション再利用が定額枠で動作している（実測）。研究が API 側の利点として挙げた Prompt Caching は、こちら側でも効いている
- API へ移すと `invoke_claude_safe.ps1` の 85% 遮断（＝**支払い上限が物理的に存在する**という安全性）を失う。目標 2 は「安く回す」ではなく「破綻しない」である

**② 「UI Toolkit へ移行して YAML 競合を回避せよ」（parallel_dev_brain_body_research）**

今は採らない。**この現場では YAML マージ競合が 1 度も起きていない。**
実装エージェントが常に 1 体・直列だからである。実際の故障は §2 の「結線の不可視」で、
これは指示書 21 のスナップショット（`docs/snapshot/scene_bindings.txt`、5KB）が
**移行コストほぼゼロで解決した。**

指示書 23 で uGUI に一本化したばかりでもある。UI Toolkit への移行は
**Body 層を並列化する必要が出たときに再検討する**（現時点でその必要はない）。

### 採らない — 時期尚早

| 主張 | 判断 |
|---|---|
| マルチコンテナ並列（選択肢 A） | Brain 分離の前にやっても、重い Unity を並べるだけ。§5 の後 |
| VPS + GameCI + Unity Accelerator | ローカル 1 台で足りている。CI 化は Brain 分離後 |
| VLM による Visual QA | 研究ノート自身が「Raycast 到達性テストのほうが安く確実」と書いている。<br>`AssertRaycastReachesButton` が既にある。VLM は文字化け検出に限れば将来価値あり |
| 自律 Devlog / SNS 自動投稿 | ゲームが完成してから |

## 5. Unity 側と Pure C# 側の境界（本書の中核）

### 境界の判定基準

> **`using UnityEngine` が要るか。要らないなら Brain。**

例外を作らない。`ScriptableObject` を使いたいという理由で Brain のロジックを
Body へ引き込まない（データ定義とロジックを分ける）。

### 現状の棚卸し — 既に半分できている

`using UnityEngine` を含まないランタイムファイルが **20 本以上**ある。

```
Core/Data/          GameState / TurnRules / CommandEffect / TrackedParameter
                    EndingKind / TerminationKind / IsExternalInit
Features/Boss/      BossState / BattleTurnResult / FullBattleResult / 各 enum
Features/Command/   CommandResult
Features/Event/     EventResult / EventTriggerKind
Features/GameFlow/  GamePhase
Features/MetaProgression/  MetaProfileState / MetaProfileDto / MetaUnlockKind
```

**これらは既に Brain の中身である。置き場所が Unity の asmdef の中なだけ。**

### 分けかた（3 段）

| 層 | 中身 | 検証 | 編集する道具 |
|---|---|---|---|
| **Brain: Pure C#** | 上記 20 本 ＋ Resolver のロジック本体 | `dotnet test`（ミリ秒） | **プレーンエディタ / AI**。Unity を開かない |
| **Bridge: SO ラッパ** | `*ResolverSO` / `*CatalogSO` / `GameRulesSO`<br>= Brain を呼ぶだけの薄い ScriptableObject | EditMode（例外 3 枚） | プレーンエディタ / AI |
| **Body: Unity** | `*View.cs` / `GameFlowController` / `Editor/` / シーン | PlayMode ＋ 目視 | AI（直列 1 体）＋ **人間の Inspector** |

**Resolver の扱いが要点である。** 現在 `MetaPointResolverSO` などは
「純粋関数だが ScriptableObject」という中間形にある。ロジックを Pure C# の static クラスへ出し、
SO は `[SerializeField]` のパラメータを持って呼ぶだけの殻にする。
そうすると計算部分が `dotnet test` の対象になる。

### 何が嬉しいか

- テストが 0.88 秒 → さらに速く、かつ **Unity 起動が不要**になる
- 実装 AI が Unity のライセンス・Domain Reload・Library ロックから解放される
- Brain 層なら実装 AI を並列に増やせる（目標 3）
- 人間が Unity を開く理由が「見る」と「置く」だけになる（目標 1）

## 6. 「今回は仕方ない」と「長期的にこうする」

### 今回は仕方ない（当面このまま。触らない）

| 対象 | 理由 |
|---|---|
| `Game.asmdef` 1 枚 | `00_rules.md` の明文。分割は Brain 切り出しと同時に ADR で決める |
| シーン中心（`MainGame.unity` 1 枚） | シーンレス化は作り直しに近い。今の資産を捨てる価値がまだ無い |
| uGUI（UI Toolkit にしない） | §4-② |
| ScriptableObject でのデータ定義 | JSON 化の利点は並列編集。単一エージェントの今は利点が出ない |
| `docs/webgl/` 13MB のリポジトリ同梱 | Pages の配信元の可能性。移すと公開 URL が変わる |
| ~~人間による Inspector 結線~~ | **仕方ないものから外した。ADR 0002 で消す。** 3 サイクル連続で壊れた唯一の場所であり、<br>ここだけは「人が触れるところ」でないのに人間の手作業が必須になっている |

### 長期的にこうする（優先順）

| # | 内容 | 効く目標 | 前提 |
|---|---|---|---|
| **0** | **Code-first Bootstrap（ADR 0002）。UI をシーンに焼かず実行時構築へ** | **1b / 2 / 3** | **最優先** |
| 1 | Brain 層を `Game.Core` として切り出す（Pure C#、`dotnet test`。ADR 0001） | 1b / 2 / 3 | 0 と独立に進行可 |
| 2 | Resolver のロジックを SO から Pure C# へ移す | 2 / 3 | 1 |
| 3 | レベル/イベントデータを JSON へ（`.asset` から） | 3 | 1 |
| 4 | Brain 層で実装 AI を複数並列に | 3 | 1・2 |
| 5 | 無人実行を GitHub Actions へ移す（決定的処理のみ） | 2 | 1 |
| 6 | VLM による文字化け・UI 重なり検出 | 1b | 0002 完了後に再検討 |

**Asset-as-Code（拡散モデルでの生成→自動インポート）は計画から削除した。**
人間がアセットを制作するため不要であり、Steam のトレーニングデータ権利要件も回避できる。
`ProceduralSpriteGenerator` は最終形ではなく、人間の制作物に差し替わるまでの仮アートとして扱う。

**0 を最優先とする。** 未バインド 15 件・3 サイクル連続の同型故障・シーン 10.6 万トークンが
同時に消えるのはここだけである。1 は独立に進められるが、2 以降は 0 と 1 の後。
