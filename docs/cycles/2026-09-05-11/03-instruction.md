# 指示書 32（B2）: 検証を常駐 Unity へ寄せる

```
ROLE: Executor
BRANCH: main
判断: 人間との直接協議。00_rules.md「運用」の検証振り分けに従う
前提: 指示書 30 の完了後。31 より先に行う（31 の検証がこの経路で速くなる）
```

## 目的

検証が遅い。1 回あたり最大 30 分かかり、無人実行が今朝それで失敗した。

原因は方式の選択にある。

```
現在   毎回 Unity を起動し直す方式（batchmode）。最大 30 分。実行中は Unity を閉じておく必要がある
既設   常駐している Unity を外から操作する仕組み（.mcp.json の unityMCP、http://127.0.0.1:8080/mcp）
```

**速いほうが既に用意されているのに、遅いほうを使っている。** これを入れ替える。

なお 2 つの方式は同時に使えない（開いている Unity があると起動し直す方式は失敗する）。
**人間を待たせる検証は常駐 Unity、無人の検証は起動し直す方式で CI** に振り分ける。
本サイクルは前者だけを扱う。

---

## 1. 実装方針

### A. 常駐 Unity 経由でテストを走らせる手順を確立する

- Unity を開いたまま、MCP 経由で EditMode / PlayMode テストを実行する
- **結果は今と同じ場所・同じ形式で出す**（`logs/editmode_results.xml` / `logs/playmode_results.xml`）
  - `mechanical_check.ps1` はこの 2 つを読んでいる。**出力先を変えれば機械判定が壊れる**
- 手順は `scripts/` に 1 本のスクリプトとしてまとめる。人間が引数なしで叩ける形にする

### B. 所要時間を実測して比較する

**本サイクルの成果はこの数字である。**

| 方式 | EditMode | PlayMode |
|---|---|---|
| 起動し直す方式（現行） | 実測値 | 実測値 |
| 常駐 Unity（本サイクル） | 実測値 | 実測値 |

同じテストを両方で 1 回ずつ走らせ、**実時間を秒で貼る。** 推定値を書かない。

### C. 手順を短く記録する

`docs/laws/` ではなく `docs/STATUS.md` に 3 行以内で書く。
「常駐 Unity でテストを走らせるにはこれを叩く」だけが分かればよい。

---

## 2. やってはいけないこと

- `scripts/nightly_gate.py` を変更しない。**あれは無人・CI 側の経路であり、起動し直す方式のままでよい**
- `scripts/mechanical_check.ps1` の読み取り先を変えない
- `.mcp.json` を変更しない
- Unity のプロジェクト設定・シーン・アセット・ゲームのコードを変更しない。
  **本サイクルはコードに 1 行も触らない**
- 不変条件・スナップショットの仕組みを変更しない
- 指示書 30 と並行して走らせない（どちらも Unity を使う）

保護対象は従来どおり。

## 3. 検証

| # | 内容 | 期待 |

## 4. 停止条件

- MCP 経由でテストを実行する方法が特定できない（**推測で実装しない。手を止めて報告する**）
- 結果の XML が今の形式で出せない
- 常駐 Unity では件数が変わる（同じテストなのに結果が違う）
- `Game/` 配下に差分が出た
